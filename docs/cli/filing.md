# The one route from a body to an issue

**Three verbs file, and one of them was a subprocess.** `forge new` files what a person or an agent
wrote, `forge feedback` files a defect against this plugin from any checkout, and the release
script's batch-review step files the reading a range of commits is owed. Two of them assembled the
same nine steps by hand out of seven shared exports, each in its own order; the third spawned the CLI
and matched two patterns against the refusal text to learn what had happened. So a rule about filing
was three edits and a test that the three agreed, and ISS-334 was about to add a fourth kind, a size
field and an unranked value to all of them.

One interface decides a filing now: the body assembled from what the route wrote and what it fills,
the shape read against the kind's sections, the duplicate, the neighbours, the fold, the rank, the
field mapping and the create. Exactly one place in this tree writes a create on the issues tool, and
a case in the suite fails with that place named when a second one appears. That check is anchored on
the tool's own name, so a create on another one — a comment, an upload — is not its business, and a
caller passing an action it was handed rather than writing one out is not a second decision about a
filing and is not counted.

**It neither prints nor exits, and both halves of that are load-bearing.** The words an outcome
earns differ per route — "filed" against "No open issue on forge-plugin carries this title" against
a release step's indented block — so the lines stay with the verb that speaks them and the module
returns a value. The exit matters more: the release step files between its push and its install,
where ending the process on a refusal would leave a release halfway done. So a refusal comes back
as parts a caller branches on — the key a duplicate was read against, and whether the shape refused
the body whatever else was open — decided where they are still values. A release step matching
patterns against a paragraph written for a person was reading the wrong artefact, and those two
parts are why it can be a caller rather than a parser. The two verbs take a wrapper that exits,
their refusals having nowhere else to go.

**A route contributes a section, and never text it joined on first.** `forge feedback` fills a
*Where* naming the plugin version, the copy that answered, the caller's project and the agent, and
*Where* is a section the bug shape reads for. A route that appended it before the shape read would
be reading a different document from the one it files; one that appended it after would file a body
the shape never saw. It arrives as a section, `withSections` places it, and `bodyOf` is what a route
calls when it wants that assembly and its shape verdict before anything reaches the tracker —
`forge feedback` asks it before it aims the project at this plugin, so a malformed note costs no
call at all.

**Two things stayed a route's own, on purpose.** The duplicate check is off for `forge feedback`,
because that verb routes a note whose title is already open into a comment on that issue: an overlap
refusal above that would refuse exactly the notes the route exists to place. And `forge feedback`'s
title match runs before the filing and buys the open-issues page the filing then reuses, so the
route that needed a reading for its own reason does not pay for a second.

**The kind table did not move up a layer.** The kinds and the sections each one's body owes are
already one declaration, and the help, the refusal and the hook's shape reader all render from it,
so the rule that a filing's sections live in one place was met where it stands. The interface reads
a body through that same reader. Lifting the table would have bought nothing and cost an edit in the
hook that reads it directly, which another change holds.
