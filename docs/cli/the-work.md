# the work — what a run leaves between two records, and who reads it

Nothing lands on the thread inside a phase. Payloads arrive at its edges, so from one edge to the
next the issue is silent about what its run is doing. That is fine for every phase but the long
one. *Owed* is the same word for a phase nobody has started and a phase whose change is staged and
blocked on six named errors, and on 2026-09-11 the second reading cost one issue its sixty-six-file
rename twice: a run arrived at a status whose record was complete, was told the truth — Phase 4 was
owed — and cut the same change again on a branch of its own. The run that had built it wrote what it
knew into a comment six minutes later. Prose on a thread is not what a claim reads.

The worklog beside the lease held the missing fact all along, and three things kept it from the
reader. No entry check named it, so a run could reach `developed` having never said where its branch
was. The verb every run calls printed the record and not the worklog. And where the worklog is
captured, the capture could not name a branch that had no commit on it yet — which is every branch
at the moment its run enters the status it will build under.

## The opening carries the pointer, and the block below carries the rest

`forge claim` and `forge resume` open with the same lines about the record, from one renderer,
because two renderers disagree about one record the first time a row moves. The work goes on that
same block rather than into a footer: the branch, the head it stands at, what it was cut from, when
that was read, and what can be reached of it. It is silent where the worklog names no branch and
where the status owes no phase, so an issue with nothing behind it reads as it always did and a
closed one names a branch that is nobody's next step.

The split between the two blocks is by fact and not by verb, because a footer that reprinted the
branch would be the second renderer under another name. The pointer is the opening's; the touched
set, the plugin copy, the review round and the dead ends are the block's. One list decides which is
which, so a fact added to the pointer leaves the block on its own rather than by somebody
remembering.

What the split settles is *which* renderer says a fact and never *whether* one is said. A status
owing no phase has no opening to carry the pointer, so the block below picks it up there, and
`forge resume --report`, which opens on no phase line at all, prints them together for the same
reason. A closed issue is where somebody asks which branch this was, and it is exactly where the
opening is right to say nothing.

## Reachability is two readings and neither is a network call

*Can I carry this on* and *has anything but this disk seen it* are different questions, and one
answer for both would leave a pushed branch and an unpushed one reading the same. So the checkout is
asked whether it resolves that commit, and asked separately whether any remote-tracking ref it holds
contains it.

Both are offline, and that is the constraint rather than a convenience: this is the line a claim
opens with, and a claim that waited on a remote would wait on one every time it ran. Which is also
the limit on what either sentence may claim. A remote-tracking ref is this checkout's memory of its
last fetch, so what it carries is said as of that fetch, and what it does not carry is said as
nothing *seen from here* — a push from another machine since is invisible to both readings, and an
offline reading that announced where the work is would be asserting the thing it declined to ask.

A head this checkout does not hold names the fetch to try **before** it names the restart. A commit
absent here may be one a fetch brings, and nothing offline tells that from work that is gone — but
where the fetch brings nothing, *start over* is the right answer and saying nothing is not. Whether
the branch was ever pushed is reported and never enforced: no CLI can tell a private remote from
none.

## The status a change is built under owes the branch

`in_progress` is refused where the worklog names no branch, and the refusal names the capture that
writes one. It is an entry check like the ones [the entry checks](the-entry-checks.md) argues, and
it reads the record alone — what git knew was written onto the issue by the capture that knew it,
and no check here opens a tree. What it does not judge is whether that branch was pushed or whether
the head it names still exists.

It is owed at every rung. A rung below the top buys away the repetition of a judgement, and a tree
the record cannot name is not a judgement repeated.

## Which is why an empty capture no longer writes nothing

`--pushed` used to write only where it found a diff, so an empty reading could not put an empty
touched set over a full one. What the measurement behind that had caught was the touched set, and
the rule was drawn one noun too wide. A branch the moment it is cut has its base for a head and no
diff at all, and that is exactly when the transition above is made — so the reading that wrote
nothing wrote nothing at the one moment the branch had to be on the record.

The pointer is now written whenever git answers, and the touched set is cleared from that same
reading. That is what the old silence was really buying: a block that is one reading of one
checkout, rather than the branch of one and the file list of another. The line the capture prints
says which of the four reasons left it with no diff, and a checkpoint offered to a landing is
refused on the diff rather than on the head, a branch carrying nothing being nothing to land.

A capture naming a branch other than the one the worklog held says which it replaced, with the time
that older block was taken. Nothing is refused for it — a run captures again from the default branch
once its change has landed, and that is the ordinary case rather than the mistake — but the checkout
is the one thing this flag exists to be deliberate about, and a silent overwrite is how a `--pushed`
typed in the wrong tree names that tree's branch as the issue's.
