# The two flows this copy serves, and what a flow may ask a project for

The axis itself — why a flow is a slug, why a directory is the whole of what it serves, and what is
refused where the key is read — is [the flow axis](the-flow-axis.md). This is the other half: which
flows exist here, and what a flow may and may not ask of the project running it.

## The two flows this copy serves

`default` is a project with no screen — a library, a CLI, a service, this plugin. `screen` is a
project whose change a person looks at, and what it serves that `default` does not is the judging:
the run acquires the identity the deployment reports, dispatches the `qa` role against it, waits,
takes a blocking finding back as work and is judged again at the identity the repair moved to. Which
findings block, and the charter its judge writes before it maps a criterion, are that flow's
verification reference.

`default` keeps the `screen change` declaration, the park it earns and the route out of the
attachment `testing` refuses a verdict without — because the declaration vocabulary is global and a
refusal a run can meet under any flow owes served text under every flow. What leaves it is what only
a screen project can act on: the screenshots, and the environment section whose every example is a
browser.


## What a flow may not decide

A flow sets which declarations a plan is *required* to make, and that list is read where the plan is
written — `requiresRefusal`, one line of `planChecked` — never at a rung. Satisfied by `yes` and by
nothing else, which is the reading `flowPolicyConflict` already gave the same list: a declaration
answered `no` is the flow's case not arising, not the flow's demand met. It does not set what a rung
demands: the entry checks are one code set, so a UI flow can require `screen` of every plan while the
screen-evidence refusal stays the single place that charges for it. Neither shipped flow requires
anything, `screen` included — a project whose changes are screens still has migrations and CLI fixes,
and a plan forced to declare a screen buys a judging round with nothing to judge — so the case that
holds the refusal plants its flow.

**A flow may also ask the project for a judgement**, and asking is the whole of what it may do:
`judge: "independent"` on the declaration, against `pipelineConfig.qa`, which is the one thing that
decides. A flow asking for what the key does not name is `forge doctor`'s conflict line naming both
sources and exiting on it, beside the release-policy one — never a reconciliation, and never a
refusal at a rung, which would be an entry check reading the flow.

**The declaration vocabulary itself is global**, and a flow may neither add a name nor remove one.
The reason is where the flags are read from: they are parsed out of the issue's *persisted plan text*
with no flow as an input, so a plan's declaration means the same thing forever. Let a flow own the
vocabulary and a plan reading `screen change: yes` parses to nothing under a flow whose table lacks
`screen` — changing a project's flow would retroactively reinterpret every plan already written, with
no check firing. A case holds the same persisted plan and the same evidence to the same verdict under
two different flows.

A flow requiring a person's look on a project whose release policy waives it is **reported, not
reconciled**: the declaration would promise a look nobody takes, and `forge doctor` prints that
conflict and the judgement one above as misses it exits on. No precedence rule between the two
sources is introduced, because there is none to introduce.

The record-contract identity stays separate. One number stamps records and is compared against what
a served text declares; neither is derived from the flow, and nothing here diverges what a rung
demands, so no record becomes ambiguous. The pin is also one value for the whole set rather than a
per-skill map: the method and the contract are co-designed, and a project mixing them runs text
nobody tested.
