# `record` — a correction names what it corrects

Three kinds are written into a field of the issue rather than onto its page: the plan, the criteria
and the release note. A second write of any other kind leaves the first standing on the page, where
the report counts it as superseded; a second write of one of these three replaces the value, and
nothing anywhere keeps the one it replaced. Two runs overwrote an earned release note that way, one
with a probe typed into a tidy-up command on a closed issue, and each found out only because it went
looking. So once the status a field's payload is earned at has been reached, a write that would
replace it with a different value is refused until a correction naming that kind stands.

**The status is read off the table of what each entry check cites**, so the plan and the criteria
are held from `approved` and the note from the status that owes it. A side status says nothing about
the lane by itself, and is read as the status its latest park left. A rung whose ladder drops the
payload at that status is never refused, since a payload the rung excused earned nothing to protect.

**One route out, not two.** The filing offered a flag on the write itself as a second way through.
A refusal carries the one command that clears it, and a correction already carries what moved and
why; a flag on a file verb would have had to grow both. The correction is written first, naming the
kind in `--corrects`, and the same write is sent again.

**Presence and recency, never the words.** A correction counts where it is whole, names the kind,
and was written after the last replacement of that kind, which is the one it spends. Whether its
sentence describes what actually moved is the reviewer's to judge: a check attempting it would pass
a dishonest one.

**The replaced value is put up before it is gone.** The write sends its uploads, then its fields,
then its comments, in that order and no other, so the old value goes up as a file ahead of the field
update, and a `Superseded payload` record posted after the field names that file and the correction
it spent, and carries the value inline where it fits one comment. A field update that fails leaves
the correction unspent, so the same write sent again goes through; a comment that fails after the
field was written leaves the value readable in the file already on the issue.

**`--corrects` is required of every correction from now on**, and the CLI's own writers supply it:
the path a landing wrote names the plan, a status set by hand names `issue:status`, a rung climbed
names `issue:complexity`, a criterion ruled the wrong test names it by number. A correction written
before the field existed reads back whole, and names nothing, so the report keeps it in the counted
list; one that names a record the report prints stands under that record instead, with the payloads
it let a write replace beneath it.
