# `record` — a rung in one call, and the move its records earn

ISS-285 measured 264 of 564 `advance` calls following a record directly, asking what the write had
just changed, and answered it by making the write say so: the line `forge advance --owed` heads its
answer with, from the one function that verb and `forge resume` also spend. On stderr, because stdout
is the record and its last line is the tag every reader keys on. Counted with the comment just
posted, folded into the page the write already read, a second fetch costing the round the line saves.
And it never fails the command a record already landed for. Saying it left the second call standing.
Measured again over 514 runner transcripts and 13,377 tool calls, `record` followed by `record` was
the commonest adjacent pair in the whole corpus at 458, and `record` followed by `advance` the second
at 248. Seven hundred pairs, and not one of them a retry, a poll or a repeat: each is a run doing the
next mechanical thing because no call did both. For scale, the largest pair that is not forced is an
edit followed by a test at 299, which is development rather than bookkeeping.

Three of the seven rungs are earned by more than one record, and the shortest complete walk of the
ladder was ten record writes and up to seven advances. Nothing was undecided between any adjacent
pair of them. A status is earned by a record, so the move is a consequence of the write rather than a
judgement after it: once the last record a rung cites is on the issue there is nothing left to weigh,
and the CLI already knows both which kinds are still missing and whether the rung is now complete —
it says so, and waits to be asked again.

So one call carries a rung. `--also <kind>` opens each kind after the first with its own payload, and
the same entry check `forge advance` reads decides, against the record as the write has just left it,
whether the status moves in that same call. The move happens only where a kind that call wrote is a
kind the rung ahead cites: a status moved by a `gap` that happened to follow the record which earned
it would be a status earned by the order of two calls rather than by a payload. A rung whose cited
set is one kind moves on that record's own call, which is where most of the 248 were. The whole tail
is on stderr, for the reason ISS-285's trailer is: stdout is the record, and its last line is the tag
every reader keys on.

## Three things had to be true first

**A refusal costs nothing already written.** Every payload of the call is judged before the first of
them is sent. Then the uploads, whose credential scan is of bytes and so cannot be judged any
earlier. Then the fields of the call in one update — a cap is measured on what the transport is about
to send, not on what the caller typed, so it cannot be checked in the judging half at all, and a
comment posted ahead of a capped field would have landed by the time that field refused. The
comments and the mark go last. What is up cannot be taken down, which this verb already promised of
an upload; a payload is what the call either writes all of or none of.

**The check reads what the tracker holds.** The fields are folded back into the record the check
reads as the update read them, never as the call submitted them: a project naming a prose language
stores a rewrite, and the plan's own comparator accepts any non-empty read-back, so a plan stored
short of a section the caller sent would otherwise be judged by the section. Where a write's effect
is in neither answer the issue and its page are read again — the merged mark, whose stamp and audit
comment are the tracker's own, and an upload, which moves the attachment set every citation of
evidence is judged against. Reusing the check buys nothing if its input is the wrong record.

**What is owed is named, not counted.** The owed line reports how many items a rung is short of, and
a run that wrote half a rung had to ask a second time which. The tail prints the missing items under
that line from the same formatter `forge advance` prints a shortfall with, so a `developed` call
carrying only a review names the merged mark.

## What is not in this verb

Which kinds a rung cites. `plugin/src/guides/phases.mjs` declares that as one table and the move
reads it there; a pairing typed into the record verb would be a second copy, free to disagree the
first time a rung's set changes — which ISS-1066 changed twice in one month — so
`plugin/test/flow/record/rung.test.mjs` asks that no module of the verb name a rung beside a kind
that rung cites.

The routes off the ladder's linear path. A park, a drop, a reopen's triage and a status set by hand
are moves a record does not earn, and a side status is left where it stands: `owedIn` drops the
routed park `targetOf` answers with, and those stay `forge advance`'s. A close is earned by no
record, so it is the one rung a run still asks for outright.

The order the owed line and a served guide part are printed in, which is ISS-968's.
