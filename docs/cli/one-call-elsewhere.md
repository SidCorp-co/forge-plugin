# One call elsewhere

**The saved slug is every run's at once.** Moving it moves the project of each run and pane already
standing in the checkout, on their next call. Before
`--project` existed, the one way to aim a single call at another project was `forge doctor --set
slug=`, and runs took it: mowment's master rewrote its record to fold a finding onto a plugin issue,
and a sibling pane then claimed and moved forge-dev's ISS-39 believing it was mowment's, the
`NO_OP` it was answered with naming no project (ISS-2910). A finding owned by another project's
row could otherwise be recorded as routed and never delivered (ISS-2563).

**A flag and never a variable.** An exported variable reaches every child process a session or a
dispatch starts, which is the shared state this exists to remove under another name. A flag is
typed on the one call it aims and nothing inherits it. The aim is `useProject` in this process's
memory, the seam [`feedback`](feedback.md) already aims through, so nothing is written to disk.

**Reads and comments only.** `forge issue` takes it for a read by key, the listing and `--search`,
and `forge comment` for the thread and a post. Beside an issue write it is refused, and the lease,
record and status verbs do not take it: a lease and a worklog are this tree's, and a status moved
from a checkout of another project is the incident above. A post takes no lease on the far issue,
the finder's route already taking none.

**What a key resolved to says which project it was.** A key missing from the aimed project, and a
status move the tracker refuses, name the project and where the aim came from — the flag, a
directory, or the saved record's path. The issue read carries the project beside its two
identifiers on every shape of it, and the thread's heading names it. A wrong record then reads as a
wrong project rather than as a success. The transport's own refusal is left as the tracker's words
with nothing on either side, as every caller that frames one reads it, so the naming is the framing
verb's.

**A claim holds the project it was taken in.** A run's key is resolved afresh on every call, and a
sibling rebinding the checkout in the middle of a run once sent that run's record onto another
project's issue of the same number, which the write took a lease on as if it were its own
(ISS-2452). So each lease a run writes keeps, per holder, the issue the key resolved to and the
project it resolved in, and a later call of the same run whose key resolves to another issue is
refused before it sends anything. The pin is the holder's and not the tree's, because the holder is
what a claim names and one git directory serves every session standing in a checkout. An aimed call
neither compares nor pins, having chosen its project; and a claim typed by the issue's id moves the
pin, which is how a run that meant the move takes the key where it now resolves.

**Rebinding still works, and says what it does.** `forge doctor --set slug=` is not refused: the
orientation file the tracker writes into a checkout is prose that nothing here reads, so refusing
on it would be a second source for the slug. What the reply adds when the value
moves is the one thing a person typing it may not know: who else it just moved.
