### `awaiting_release` — reads the verification, against the plan's flags and the release note field

The rung promises *the change is running where it landed*, and it is the deploying actor's: the
verification is of code already out, which is why it is a rung of its own and not something the
judge's record can answer for.

**Which deployment answers that promise is the route's own.** Where the default branch's landing
deploys to production, it is the deployment that landing built; where production is a separate branch
promoted to, it is the deployment the promotion built, and a reading of the other answers nothing
here. The verification is that deployment's reported identity held against the change that landed,
and a stale or unrelated identity leaves the rung unearned.

The rung is where merged work waits for production, so the verification is read against what landed.
Where the production branch is a different one, promotion is a step outside this ladder, and whether
a person is waited for is the project's answer. Close it in the same run: no comment decides the
close, and a thread too long to return whole cannot refuse it.

**A failed reading is the release actor's to repair forward.** The actor that promotes and deploys
takes no way back from here: it repairs in the same direction, or hands the release over carrying
what it observed. That obligation is the release actor's alone, and says nothing about the route a
run shipping its own change takes when its ship fails.
