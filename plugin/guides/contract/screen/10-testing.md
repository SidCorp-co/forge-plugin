### `testing` — reads the verdicts, against the criteria and the plan's flags, and every finding folded onto the issue

The rung promises *the evidence is here to be judged*. The verdicts are what earns it, so it is the
judge's record that gets an issue here: where a project asks for a judgement other than the
builder's, the run that wrote the code is not the run whose verdicts this rung reads. What is owed
once an issue is here is the deploying actor's, which is the rung above.

Judge every criterion on every outcome, not only on failure. A criterion is a claim too: correct one
the review proved impossible, in the open, and judge it as corrected. A verdict on the old wording
passes a claim the code cannot make.

Every finding the fold landed on the issue is answered before this rung, because the criteria field
names only what the issue was opened for and a finding judged by nothing closes with the issue. It
arrives as a comment ending in a `folded` record, and `forge advance <ref> --owed` names it by its
handle. A criterion naming that handle carries it, written by the route a wrong criterion takes, so
the verdicts judge it with the rest; `forge record declined` says why it is not fixed here. `approved`
asks the same of each finding already on the issue, and a finding that lands after the judging keeps
each later rung waiting on its answer and on its criterion's verdict.

A reopen sends the judging back to its start, so a ruling on a person's finding takes the verdicts
with it. What a verdict is judged at, and what the landing has to say for one taken before it, is
`forge guide contract earning-and-unearning`.
